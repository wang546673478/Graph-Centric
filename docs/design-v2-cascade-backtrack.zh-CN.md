**语言:** [English](design-v2-cascade-backtrack.md) | [简体中文](design-v2-cascade-backtrack.zh-CN.md)

## 1. 设计哲学

### 1.1 核心命题

> **每一个 Agent 任务本质上都是对关系图的操作。
> 图是编制者的计划，而非事件的被动记录。**

Graph-Centric Agent Harness 为**弱但便宜的模型**构建——本地部署、小上下文、
会犯错的模型，需要结构化重试而非一次性精确命中。设计赌注是：一个纪律严明
的 Harness 可以通过强制执行以下约束，从不稳定的模型中提取可靠的结果：

- **结构化状态**（关系图）作为唯一工作记忆
- **级联回溯**——下游出错时，修复下游，验证上游
- **不可变锚点**——用户意图永远不会被模型悄悄改写

### 1.2 为什么需要这个

当前 Agent 框架（LangGraph、CrewAI、AutoGPT）假设强模型能一次规划正确。
它们优化吞吐量——一次分解，并行调度，合并结果。子任务失败时，孤立重试。

这对 GPT-4/Claude Opus 有效。对 DeepSeek-v4-flash、本地 Llama 以及任何
初始计划大概率错误的模型，它会崩溃。

**这个 Harness 为第二种场景设计。**它将每次失败视为可能使上游假设失效的
学习信号，并进行相应验证。

## 2. 关系图

### 2.1 三层架构（L0 / L1 / L2）

| 层 | 名称 | 内容 | 可变性 |
|----|------|------|--------|
| **L0** | 骨架 | 节点 + 边（结构） | 通过补丁可变 |
| **L1** | 肌肉 | 每节点 `{responsibility, implementation, design_intent, constraints}` + 置信度 | 通过重新充实可变 |
| **L2** | 皮肤 | 原始字节（源文件、配置、schema） | 从不存入图；按需读取 |

L0 告诉你*什么依赖什么*。L1 告诉你*为什么*和*怎么做*。L2 是真实数据——
图所描述的实际文件、配置、数据。

### 2.2 节点类型

图中的节点分为两类：

**确定性节点**——模型知道如何实现，置信度高。例如："创建一个包含 `<canvas>`
元素的 HTML 页面。"

**探索性节点**——模型不知道如何实现，需要通过搜索、实验或用户澄清来发现
方法。例如："实现蛇的移动控制逻辑。"

两种类型共存于同一图上。模型标记其不确定的节点，这些成为探索和修复的目标。

### 2.3 锚点节点（根节点）

根节点 **A** 代表用户意图——用户陈述的任务。它：

- **不可变。** 模型永远不能重写、删除或替换 A。
- **回溯终点。** 所有级联验证在 A 处停止。
- **用户唯一介入点。** 如果回溯到达 A 且 A 本身被发现有歧义或不可行，
  Harness 将问题呈现给用户进行澄清。

A 在数学意义上并非"绝对正确"。它是由*用户权威锚定*的——模型不能悄悄将
"重构认证模块"重新解释为"从头构建新认证模块"或"认证模块不存在，我去
重构日志模块"。如果现实与 A 矛盾，通知用户。

## 3. 核心循环

### 3.1 概述

```
用户提供：锚点 A + 期望结果 D

┌─────────────────────────────────────────────────────────┐
│                                                         │
│  1. 规划: Main agent 读取图，搜索网络/知识库，          │
│     产生路径 A→B→C→...→D                                │
│                                                         │
│  2. 执行: Sub-agents 逐步执行各个节点                    │
│                                                         │
│  3. 节点 K 失败时:                                      │
│     ├── Main agent 自动重新规划 K 及下游路径              │
│     ├── 级联回溯: 沿所有入边向 A 验证 K 的前驱           │
│     └── 保留中间结果；只验证不重执行                     │
│                                                         │
│  4. 重复直到从 A 到 D 的所有节点通过验证                 │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 3.2 阶段状态机

```
                    ┌──────────┐
                    │  规划    │ ← 规划、验证、修复
                    └────┬─────┘
                         │ 图验证通过
                         ▼
                    ┌──────────┐
                    │  执行    │ ← 分解、调度子代理
                    └────┬─────┘
                         │
              ┌──────────┼──────────┐
              │          │          │
              ▼          ▼          ▼
          全部成功    图错误     任务错误
              │          │          │
              ▼          ▼          ▼
           审查      级联回溯    抛给调用方
              │          │
              ▼          ▼
           完成     重新规划
                    验证上游
                       │
                       ▼
                    回到规划阶段
```

### 3.3 Main Agent 职责

Main agent（Proposer）是**唯一规划者**。它：

1. **搜索**——网络、知识库、代码库——发现类似问题如何被解决
2. **规划**——在图上产生节点和边
3. **区分**已知节点和探索性节点
4. **自动重规划**——子代理失败时，重新设计失败节点及其下游路径
5. **仅在 A（锚点）有歧义或期望结果 D 不明确时**请求用户澄清

Main agent 不直接执行任务。它通过 `explore` 步骤（只读调查）或 Task 阶段
调度将所有执行委托给子代理。

### 3.4 Sub-Agent 职责

子代理是**单次执行器**。每个子代理：

1. 接收节点规格（L0 + L1 + 相关 L2 上下文）
2. 执行工具（bash、web 等）来完成任务
3. 报告以下之一：
   - `success`——节点完成，输出了结果
   - `report_graph_error`——现实与图在此节点矛盾，附结构化证据

子代理**不**编辑图。它们**不**做规划。它们**不**决定下一步做什么。
它们是工作者，不是思考者。

## 4. 级联回溯

### 4.1 原理

> **关系图中的节点默认是耦合的。**
> 当下游节点改变时，其前驱必须被验证。

这是与当前 Agent 框架的根本区别。大多数框架假设节点独立——修复节点 C
不影响节点 B。我们假设相反：**B 是为服务 C 而设计的。如果 C 变了，
B 可能不再适用。**

### 4.2 算法

```
节点 K 失败时：

1. Main agent 重新设计 K → K'（以及可能的 K 下游路径）

2. 从 K' 级联回溯：
   对于 K' 的每个前驱 P（沿所有入边）：
   
   a. 验证: P 的设计在 K' 的新需求下是否仍然合理？
      - 检查 P 的设计逻辑（L1: responsibility, implementation, design_intent）
      - 检查 P 的输出（P 的结果能否喂给 K' 的预期输入？）
   
   b. 如果 P 通过两项检查 → P 保持原样，继续回溯
   
   c. 如果 P 未通过 → 标记 P 需要修复，从 P 继续回溯
      （P 的前驱可能也需要验证）
   
   d. 如果 P 的设计正确但输出错误 → 重新执行 P
      （不重新设计），刷新输出，继续回溯
   
   e. 到达 A 时停止（A 不可变——如果 A 本身有问题，呈现给用户）

3. 回溯完成后：
   - 重新执行任何输出失效的节点
   - 从最深的已修复节点继续向前执行
```

### 4.3 验证决策

每一步回溯的验证由**模型**执行，而非固定的规则引擎。模型接收：

- 前驱的 L1（设计描述）和最后一次输出
- 后继的新 L1（更新后的需求）和预期输入
- 原始任务上下文

并决定：*此前驱是否仍然适用于新后继？*

这是模型驱动的原因：
- 代码任务可能需要实际执行测试
- 非代码任务可能需要语义比较
- 验证策略取决于具体领域

### 4.4 中间结果保留

当回溯验证节点的设计为正确时，节点的输出被**保留**。只有验证失败的节点才
重新执行。这使得回溯成本与*变更范围*成正比，而非*链的长度*。

### 4.5 DAG 支持

级联回溯适用于任意 DAG，不仅是线性链：

```
        → B1 →
    A →       → D → E
        → B2 → C →
```

如果 C 失败并被重新设计为 C'：
- B1（通过 D）和 B2（直接）都是需要验证的前驱
- 回溯沿变更节点的**所有入边**进行
- 验证扇出受图入度限制
- 每条分支独立向 A 回溯

## 5. 探索与规划

### 5.1 规划的两个阶段

**初始规划（从零开始）：**

用户只提供 A 和 D，没有中间节点时：

1. Main agent 搜索网络/知识库寻找类似问题
2. Main agent 识别可以自信设计的节点（确定性）
3. Main agent 识别不确定的节点（探索性）
4. Main agent 生成初始图：已知节点填充好，探索性节点标记为占位符
5. 开始执行；探索性节点将触发子代理调查，并可能产生 `report_graph_error`
   以触发重规划

**重规划（失败时）：**

子代理 K 报告失败时：

1. Main agent 接收失败证据
2. Main agent 搜索 K 的替代方案
3. Main agent 生成 K'（并可能修改 K 的下游路径）
4. Main agent 从 K' 触发级联回溯

### 5.2 多路径探索

当 main agent 发现多个候选方案时：

```
目标 A → 搜索 → 找到三条候选路径：
  路径 1: A → B  → C  → D
  路径 2: A → X  → Y  → D
  路径 3: A → P  → D
```

Harness 支持两种策略，由模型选择：

- **深度优先**：选择最有希望的路径，完全执行。如果失败，在失败点
  回溯并尝试下一个候选方案。
- **广度优先探测**：沿每条候选路径派出轻量探索子代理，各执行固定少量
  步骤。使用它们的发现来选择最佳路径，然后再投入完全执行。

### 5.3 已知 vs 未知节点（示例）

任务："构建一个简单的贪吃蛇网页小游戏"

```
确定节点（模型知道怎么做）：
  ├── HTML 页面结构搭建              [confidence: 0.9]
  ├── Canvas 渲染设置               [confidence: 0.85]
  ├── 食物随机生成                  [confidence: 0.9]
  └── 分数显示                      [confidence: 0.9]

不确定节点（需要探索）：
  └── 蛇的移动控制逻辑               [confidence: 0.3]
       ├── 键盘输入处理              [confidence: 0.5]
       ├── 游戏循环/动画帧           [confidence: 0.4]
       └── 碰撞检测                  [confidence: 0.6]
```

模型构建图时填充确定节点。探索性节点"蛇的移动控制"成为子代理调查的焦点。
如果子代理尝试的实现失败，main agent 仅重新规划该节点及其下游依赖，
然后级联回溯验证上游节点是否仍产生兼容的输出。

## 6. 收敛保证

### 6.1 硬预算

- **每次运行 300 轮。** 每轮是状态机的一次 `step()` 心跳。一轮可以是：
  一次 Proposer 步骤、一次子代理调度、一次验证、或一次级联回溯检查。
- 预算耗尽时，Harness 停止并呈现：
  - 当前图状态
  - 哪些节点成功、哪些失败
  - 最后一次失败的证据
  - 请求用户指导

### 6.2 用户介入点

用户在恰好两种情况下介入：

1. **锚点歧义（执行前）。** 如果 A 或 D 不清楚，main agent 在绘制任何
   图节点之前发出 `ask_user`。
2. **预算耗尽 / 锚点层面矛盾。** 如果 300 轮后未收敛，或级联回溯到达 A
   且发现 A 本身不可行，将证据呈现给用户并请求指导。

在这两个点之间，Harness 自主运行——main agent 重规划，子代理执行，
级联回溯验证，全部无需用户交互。

### 6.3 为何收敛

设计收敛（或以清晰信号终止）因为：

- **A 是固定的。** 回溯终点不可变——用户意图之后没有无限回归。
- **每次重规划都在学习。** Main agent 看到失败证据并搜索替代方案；
  它不会重试相同方法。
- **图在知识上是单调的。** 即使是失败尝试也增加了信息——
  "这种方法不行"记录在 L1 中，防止模型重试同一死胡同。
- **预算是硬的。** 300 轮对复杂任务足够慷慨，但有限以保证终止。

## 7. 与当前实现（v1）的对比

| 方面 | 当前 v1 | v2 级联回溯 |
|------|---------|------------|
| **锚点节点** | 无——任何节点可被补丁修改 | A 不可变，回溯终点 |
| **子代理失败时** | `GraphInvalid` 抛给调用方；调用方决定 | Main agent 自动重规划；触发级联回溯 |
| **失败范围** | 局部修复——仅修复失败节点 | 级联——验证所有前驱到 A |
| **节点耦合假设** | 节点相对独立 | 节点默认耦合 |
| **验证方式** | 固定三层（结构+模型+L1采样） | 模型驱动，领域自适应 |
| **中间结果** | 跨重规划不保留 | 保留，回溯时仅验证 |
| **用户参与** | 每次 `GraphInvalid` + `Paused` 时 | 仅在锚点歧义或预算耗尽时 |
| **轮次预算** | 50（max_rounds 默认值） | 300 |
| **目标模型** | 任意模型（双层 fast/deep） | 弱但便宜的模型（本地、小上下文） |
| **收敛论证** | 保险丝（卡住检测、修复预算） | 结构化：单调知识 + 固定锚点 + 硬预算 |

## 8. 实施路线图

### 阶段 1: 图基础变更

- [ ] 向图类型添加 `Node::immutable` 标志
- [ ] 添加 `Anchor` 节点类型或元数据标记
- [ ] 实现 `Graph::predecessors_of(node) -> Vec<NodeId>`（入边遍历）
- [ ] 实现 `Graph::path_to_anchor(node) -> Vec<NodeId>`（回溯路径）

### 阶段 2: 级联回溯引擎

- [ ] 新组件：`CascadeBacktracker`
  - `backtrack_from(node: NodeId, graph: &Graph) -> CascadeResult`
  - 对于变更节点的每个前驱 P：
    - 调用模型验证 P 的设计和输出是否满足新后继的需求
    - 返回 `Preserved | NeedsRepair | NeedsReexecution`
  - 对需要修复的前驱递归
  - 在锚点节点处终止
- [ ] 模型驱动验证提示模板

### 阶段 3: 失败时自动重规划

- [ ] 修改 `GraphLoop::step_task_stub()`——收到 `report_graph_error` 时：
  - 不将 `GraphInvalid` 抛给调用方
  - 将失败证据反馈给 main agent（Proposer）
  - Main agent 为失败节点及下游生成新计划
  - 将新计划作为 `GraphPatch` 应用
  - 触发级联回溯
- [ ] 300 轮预算配置
- [ ] 预算耗尽 → 用户友好输出

### 阶段 4: 用户介入精化

- [ ] Proposer 中的锚点歧义检测（已部分实现为 Mode B / `ask_user`）
- [ ] 预算耗尽输出格式：图状态 + 失败证据 + 指导请求
- [ ] 用户以澄清的锚点恢复

### 阶段 5: 优化

- [ ] 跨回溯轮次的中间结果缓存
- [ ] 多前驱 DAG 节点的并行回溯
- [ ] 多路径探索的广度优先探测模式

## 9. 设计原则（更新版）

这些扩展了 `ARCHITECTURE.md` 中记录的 v1 原则：

1. **模型无关。** 绝不硬编码模型名称。所有模型选择通过 `ModelConfig` 流转。

2. **时间换空间（正确性优先）。** 多次小精确修正优于少量批量修正。
   每次失败都是精确信号。

3. **级联修复，绝不孤立。** 下游节点变更时，必须验证上游依赖。
   节点耦合是默认假设。

4. **锚点不可变。** 用户意图（节点 A）绝不被悄悄改写。
   所有回溯在 A 处终止。仅用户可修改 A。

5. **通用性在模型，结构在图。** Harness 跨领域通用。领域特定判断
   （包括验证策略）委托给模型。

6. **扫描器是种子，不是产品。** 从扫描器来的低置信度起始图；
   模型才是真正的图构建者。

7. **知识单调性。** 即使是失败尝试也增加信息。图在理解上只进不退。

8. **弱模型优先。** 为会犯错的模型设计。对弱模型有效的 Harness
   对强模型更有效；反过来不成立。

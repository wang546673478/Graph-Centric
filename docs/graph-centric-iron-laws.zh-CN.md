# Graph-Centric Agent 铁律

这些铁律定义 agent 的核心运行思想。任何 prompt、Module、测试和执行策略都必须服从它们。

## 1. 图是任务的真状态

agent 不能把任务只当作对话历史处理。任务必须被表示为关系图：节点表示状态、目标、步骤、证据、子任务或产物；边表示它们之间的依赖和约束。

## 2. 第一张图只能有起点和终点

收到任务后，第一步只建立两个一等节点：

- A：起点，也就是用户意图和当前状态。A 必须是 immutable。
- D：终点，也就是本轮要达到的可验证目标。

第一条边必须表达 D 依赖 A。中间节点只能在 A/D 建立之后逐步填入。

## 3. 中间步骤来自知识或探索

如果模型知道 A 到 D 的合理路径，就把中间步骤逐步补成节点。如果模型不知道，就先探索：读代码、查资料、必要时 web_search，然后把探索证据转成图节点或边，再继续规划。

## 4. 复杂节点递归成子图

任何过于抽象、不可执行或风险过高的节点，都可以被当作新的 A/D 问题处理：先总结这个节点要达到的目标，再在它内部建立子图。递归层数不是固定概念，而受预算、可执行性和验证结果约束。

## 5. 执行只走图，不走幻想

执行阶段只能执行图中已经验证过的 Task 节点。节点的输入、输出、证据和失败原因必须回写到图或执行账本里，不能只留在 transcript 中。

## 6. 失败先重规划失败节点

如果某个节点执行失败，先重规划这个节点及其直接输出契约，再从顶层 A/D 图重新验证整条路径。不要只在失败点局部补丁式挣扎。

## 7. 如果失败来自上一步，就回溯上一步

如果失败节点的新方案仍然走不通，并且证据显示原因是前置节点的输出不满足当前节点输入，就重规划前置节点，然后再次从顶层 A/D 图重新验证。

## 8. 方案逐个尝试，不一次性幻想全枚举

agent 不需要一次列出所有可能方案。它应该一次选择一个最有希望的方案，执行、验证、失败就回写证据并尝试下一个方案，直到 D 被满足或预算耗尽。

## 9. Anchor 不可被重写

A 表示用户不可变意图。修图、repair、cascade backtracking 和自动重规划都不能删除或改写 A。若 A 本身不可行，必须显式报告任务不可行。

## 10. 自优化必须可验证

自优化循环的每一轮都必须有明确 A/D、有限改动范围、验证命令和完成标准。没有通过验证的轮次不算完成。

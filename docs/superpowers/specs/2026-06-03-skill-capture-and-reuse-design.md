# Skill Capture & Reuse — Reifying Successful Runs as Reusable Skills

**Date:** 2026-06-03
**Status:** Approved (pending spec review)
**Scope:** New feature: auto-capture successful agent runs as skills; surface them in future prompts.

## 1. Context

The harness produces rich artifacts on every successful run:

- L0 relationship graph (the structure of what was learned)
- L1 descriptions (`{responsibility, implementation, design_intent, constraints}` per node)
- L2 raw content (via `SourceLoader`, on demand)
- Review verdict (provenance)
- Full transcript (forensic)

Today these land in `demo_output/agent_a_*` and stay there. A future agent that could benefit from a past run has no way to discover or re-use it. **Successful runs don't accumulate as reusable knowledge.**

The core insight (from the user): a successful run already encodes a complete skill. The L0+L1 graph **is** the procedure (nodes = steps, edges = step-to-step relations, L1 = "what / how / why / constraints" per step). No distillation or re-encoding is needed — the graph is the native format.

What's missing from the graph: **trigger** (when to apply this skill), **provenance** (when did it run, what was the verdict), and **retrieval** (how does a future agent find it). We add these three without re-encoding the procedure.

## 2. Goal

When a run completes with `Reviewer` verdict `Done(pass)`:
1. The graph + task + review are saved as a **skill** (one directory per skill, slug-based ID).
2. A one-sentence **trigger** is generated by a fast LLM, asynchronously, describing when this skill applies.
3. Future agent invocations list available skills (slug + trigger one-liner) in the Proposer's system prompt, so the model can reference them by name.

The skill is *self-describing* — its own graph + L1 + L2 tell the future agent what it knows. The trigger is just the index entry.

## 3. Non-goals (YAGNI)

- ❌ No CLI for skill management (`list`, `promote`, `delete`, `show`). v1 uses the filesystem; promote = `cp -r ~/.local/share/graph-centric/skills/<slug> skills/`.
- ❌ No embedding-based retrieval in v1. The LLM decides relevance by reading the one-liner list. Embedding is a v2 plug-in.
- ❌ No skill versioning or diff. Saving overwrites; deletion is `rm -r`.
- ❌ No L1 quality gate (e.g., "min confidence to save"). L1 is what it is; the user can delete bad skills manually.
- ❌ No automatic skill deduplication. Same task twice = two skills with different slugs; user merges if needed.
- ❌ No re-validate-on-load. We trust the saved version; the harness re-runs the graph through Verifier on next use.
- ❌ No L2 in the skill directory. L2 is read on demand via the existing `SourceLoader` infrastructure.
- ❌ No skill graph-linking (a skill referencing another skill's slug). Just standalone directories.
- ❌ No "partial success" capture. Only `Done(pass)` triggers.

## 4. Design

### 4.1 Skill directory structure

```
skills/                                                ← repo, "approved"
└── <slug>/
    ├── task.md        # original task prompt (the input)
    ├── graph.json     # L0 + L1 graph (the procedure)
    ├── review.json    # ReviewResult (provenance)
    ├── trigger.md     # 1-sentence "This skill applies when..." (fast LLM)
    └── meta.json      # { created_at, task_id, model, domain_tags, l1_avg_confidence }

~/.local/share/graph-centric/skills/                   ← local, "experimental"
└── <slug>/... (same structure)
```

- **Slug** = LLM-generated short name (e.g., `plan-relocation-bjs-sha`, `refactor-rust-traits`).
- The two storage roots are searched in order: **local first, then repo**. On slug collision, local wins.
- New saves always go to **local**. Promotion to repo is user-driven (`cp -r` or future CLI).

### 4.2 Capture flow (async, fire-and-forget)

Triggered when a run reaches `LoopState::Done(FinalResult)` AND the embedded `ReviewResult` has `JudgeVerdict::Pass`. The caller (e.g., `bin/agent_a.rs`) detects this and calls `skills::capture::capture_skill(...)`. The function spawns a tokio task and returns immediately — the user sees `Done` instantly; the skill lands 1-3 seconds later.

Inside the spawned task:

1. **Build the in-memory `Skill` struct** with everything we already have: `graph`, `task`, `review`. No I/O yet.
2. **Generate slug** — fast LLM call: *"Given this task and graph, generate a 3-5 word kebab-case slug. Output the slug only, no prose."* ~1s.
3. **Generate trigger** — fast LLM call: *"Given this task and a one-line summary of the graph, write a single sentence starting with 'This skill applies when user asks about...' Output the sentence only, no prose."* ~1-2s.
4. **Compute `l1_avg_confidence`** — mean of all L1 confidences in the graph, or 0.0 if no L1 entries.
5. **Compute `domain_tags`** — `["code", "infra", "research", "business", "data"]` based on the L0 node kinds present. (Cheap heuristic, LLM refinement deferred.)
6. **Serialize** to the local skill root.
7. **Log** at `info!` level: `skill captured: <slug> (l1_conf=0.85, 2.1s)`.

**Error handling:** if any LLM call fails, the function logs the error at `warn!` and **does not save the skill**. The user sees a warning in logs but no `Done`-state contamination. Retry is the user's call (re-run the task). No partial-save mode in v1.

### 4.3 Retrieval flow (Proposer integration)

When the Proposer builds its system prompt, it appends a `## Available skills` section populated from the local + repo skill roots:

```markdown
## Available skills (auto-curated from past successful runs)

- **plan-relocation-bjs-sha**: "Plan a city-to-city relocation, comparing cost, schools, and logistics"
- **refactor-rust-traits**: "Refactor Rust generic trait bounds while preserving API surface"
- **cargo-build-debug**: "Diagnose `cargo build` failures from stderr patterns"
```

The model sees this list and can:
- Reference a skill by slug in its `rationale` field, signaling "I'm using the approach from skill X"
- Read a skill's `graph.json` or `trigger.md` if it wants more detail (via file tools or system prompt context)

The list is **plain prose, one line per skill**, capped at 20 skills in v1 (if more, take the most recent N; older skills are git history anyway). v1 lists all skills in chronological order; a future filter (by domain, by recency) can be added without changing the Proposer interface.

### 4.4 Storage layout

```
skills/                                  ← git-tracked, "approved"
~/.local/share/graph-centric/skills/     ← local-only, "experimental"
```

The `~/.local/share/graph-centric/` path follows the XDG Base Directory spec on Linux/macOS. On Windows, use `%LOCALAPPDATA%\graph-centric\` (deferred to v2 — v1 is Unix-only for the local root; Windows users just don't have a local root and all skills go to repo).

The **local root** is created on first save (`std::fs::create_dir_all`).

### 4.5 Module structure

New module `src/skills/` with the following files:

```
src/skills/
├── mod.rs        # re-exports, public API
├── types.rs      # Skill, SkillMeta, SkillRef, CaptureError
├── storage.rs    # SkillStorage trait, LocalSkillStorage, RepoSkillStorage, CompositeSkillStorage
├── capture.rs    # capture_skill() (async, fire-and-forget)
├── retrieve.rs   # list_for_prompt() (sync, called from Proposer)
└── slug.rs       # generate_slug() (async LLM call)
```

`retrieve.rs` has no LLM call in v1; it just reads storage and formats. The LLM "decide which skill is relevant" decision happens *inside the Proposer* when it reads the section.

### 4.6 API surface

```rust
// types.rs
pub struct Skill {
    pub slug: String,
    pub task: String,
    pub trigger: String,
    pub graph: Graph,        // L0 + L1
    pub review: ReviewResult,
    pub meta: SkillMeta,
}

pub struct SkillMeta {
    pub created_at: String,             // ISO 8601
    pub task_id: Option<NodeId>,
    pub model_used: String,             // which model generated slug+trigger
    pub domain_tags: Vec<String>,
    pub l1_avg_confidence: f64,
}

pub struct SkillRef {
    pub slug: String,
    pub trigger: String,
}

// storage.rs
pub trait SkillStorage: Send + Sync {
    fn list(&self) -> Result<Vec<SkillRef>, SkillError>;
    fn load(&self, slug: &str) -> Result<Skill, SkillError>;
    fn save(&self, skill: &Skill) -> Result<(), SkillError>;
    fn local_root(&self) -> Option<PathBuf>;   // for "promote" tooling
    fn repo_root(&self) -> PathBuf;
}

pub struct CompositeSkillStorage {
    local: Option<LocalSkillStorage>,
    repo: RepoSkillStorage,
}

// capture.rs
pub fn capture_skill(
    graph: Graph,
    review: ReviewResult,
    task: String,
    task_id: Option<NodeId>,
    model: Arc<dyn Model>,
    storage: Arc<dyn SkillStorage>,
) -> tokio::task::JoinHandle<()>;
// Returns immediately; the JoinHandle lets the caller log on completion or
// abort. The caller typically just discards it.

// retrieve.rs
pub fn list_for_prompt(storage: &dyn SkillStorage) -> String;
// Returns the formatted "## Available skills" section, or "" if no skills.
```

### 4.7 Wiring

- `bin/agent_a.rs` calls `skills::capture::capture_skill(...)` when the loop returns `LoopState::Done(_)` AND the saved `ReviewResult` is `Pass`. The returned `JoinHandle` is discarded.
- `agent::proposer::GraphProposer::build_system_prompt` calls `skills::retrieve::list_for_prompt(storage)` and appends the result to the system prompt. The Proposer gets a `Option<Arc<dyn SkillStorage>>` field (default `None`); when set, skills are listed; when `None`, no section.
- The Proposer does **not** call LLM to decide which skills are relevant. The LLM decision happens implicitly when the Proposer reads the system prompt section and writes its own rationale.

### 4.8 Slug generation

The fast LLM is given:

```
Task: <task.md content>
Graph summary: <one-line L0 summary: e.g. "5 files, 8 imports, 2 tasks">

Generate a 3-5 word kebab-case slug (lowercase, hyphens only) that names
this skill. Examples: plan-relocation-bjs-sha, refactor-rust-traits,
cargo-build-debug, write-marketing-blog.

Output ONLY the slug. No prose, no quotes.
```

If the LLM returns something that doesn't match `^[a-z0-9-]+$` (after trimming), the function falls back to `format!("task-{:x}", std::hash::Hasher)` computed over the task string (using `std::collections::hash_map::DefaultHasher`) — deterministic and never collides with LLM slugs in practice.
